# AskTube

## Implementation Summary

AskTube is a YouTube-inspired application for indexing playlists and retrieving their stored metadata and videos. Playlist ingestion validates a YouTube playlist ID, retrieves playlist metadata and paginated video metadata through the YouTube Data API v3, and persists the result idempotently in PostgreSQL. Stored playlist retrieval reads PostgreSQL directly and preserves video ordering without calling YouTube.

AskTube now also provides synchronous YouTube video transcript extraction for a standalone stored video ID. Transcript data is retrieved through the dedicated transcript provider service, normalized without changing spoken content, and returned with numeric timestamps. Transcript data is persisted as structured JSON and returned from PostgreSQL when already stored.

Transcript extraction is deliberately separate from the YouTube playlist metadata service. The transcript service checks PostgreSQL first, returns a valid stored transcript without contacting YouTube, and otherwise selects an available transcript deterministically, normalizes segment text, preserves numeric timing, persists the structured result, and returns the response.

## Current API Endpoints

- `GET /api/playlists/{playlist_id}`
  - Retrieves playlist metadata and videos from the YouTube Data API and upserts them into PostgreSQL.
- `GET /api/playlists/{playlist_id}/stored`
  - Retrieves a previously indexed playlist and ordered videos from PostgreSQL only.
- `GET /api/videos/{video_id}/transcript`
  - Retrieves and normalizes transcript segments for a YouTube video.
  - Optional `language` query parameter requests a preferred language.

Transcript errors are controlled: invalid IDs return 422, unavailable videos and unavailable transcripts return 404, and provider failures return 502.

## Transcript Contract

The transcript response contains:

- `video_id`: YouTube video ID.
- `language`: provider language code, or `null` when unavailable.
- `is_generated`: provider generated/manual metadata, or `null` when unavailable.
- `segments`: ordered transcript segments.
- Each segment contains `text`, numeric `start` seconds, and numeric `duration` seconds.
- `total_segments`: number of returned segments.

Text is trimmed and repeated whitespace is normalized. Meaningful punctuation, words, segment boundaries, and fractional timestamps are preserved.

Actual implementation flow:

- Frontend sends playlist requests to FastAPI routes.
- The YouTube-backed ingestion route calls the YouTube service, then the playlist repository, then PostgreSQL.
- The PostgreSQL-backed stored retrieval route calls the repository directly and returns the persisted playlist without any YouTube request.
- Repository code contains no YouTube logic and is responsible only for database reads/writes.

## API Endpoints

Available playlist endpoints:

- GET /api/playlists/{playlist_id}
  - YouTube-backed ingestion and upsert.
  - Fetches from the YouTube Data API, persists metadata and videos, and returns the playlist response.

- GET /api/playlists/{playlist_id}/stored
  - PostgreSQL-backed stored retrieval.
  - Reads the persisted playlist and videos from PostgreSQL only.
  - Returns 404 with "Playlist has not been indexed yet." when missing.

## Database

Playlist model
- playlist_id: primary key, stores the natural YouTube playlist identifier.
- title, description, thumbnail, channel_id, channel_title, published_at.
- created_at, updated_at.

Video model
- id: internal primary key.
- video_id
- playlist_id: foreign key to playlists.playlist_id.
- title, description, thumbnail, position, published_at, video_url, duration, available.
- created_at, updated_at.

Relationships and constraints
- One playlist has many videos.
- Each video is unique by (playlist_id, video_id).
- Position is stored and preserved as the canonical ordering for playlist playback and retrieval.
- Database reads order videos by position ASC, then video_id ASC as a stable tie-breaker.
